# Memory corrections and source withdrawal

The memory workspace inspector supports managed corrections when the backend advertises the capability. Opening a record, reading its mapping or viewing history does not adopt it.

Before the first adoption, the inspector explains that managed mode applies to the entire memory bank. When the server advertises writer capabilities, the workspace shows append, automatic extraction and FIFO support separately. Accepted work can still be waiting for publication. Deployment requires operators to drain legacy writers and verify untracked tasks. Servers without these capability fields retain the older restricted-mode explanation. Existing unadopted records remain readable. Coordinated enable, disable and forget actions remain available where the backend supports them; permanent source tombstones cannot be re-enabled.

Corrections target the current revision. Replace its content or supply a single exact text patch, enter a reason (at most 1,024 characters) and preview the result before submitting. Changing the draft invalidates the preview. A conflict requires a refresh and a new preview. Historical content remains read-only, and a manual correction is labelled as a user assertion rather than a verified fact.

A submitted operation may still be pending. The inspector reads publication and index synchronization separately; reading status never advances work. An explicit reconciliation action can resume pending work using its original operation. When a request times out or its commit is unconfirmed, retain that operation ID and inspect it instead of resending the command.

Ordinary append returns a raw-publication operation with decimal-string message IDs and a separate extraction queue state. An indexed raw conversation with a pending or unknown queue acknowledgement is not shown as wholly ready. A submitted task is not completed extraction, and a raw-only bank reports that no extraction task is required. This operation does not certify extracted facts.

Source withdrawal is separate from forgetting one record. It permanently stops normal supply of the source and its tracked derived memories, redacts their managed history and records physical cleanup separately. It does not promise to erase backups or unrelated copies. Registering an unmanaged source requires an explicit acknowledgement of the same bank-wide activation effect.

A confirmed permanent source state immediately removes its normal-supply bodies from this bank's list, recall, selected-content and known dependent revision caches. Other sources remain. Old in-flight reads are cancelled without restoring their previous snapshots; an offline or failed refetch cannot restore the removed bodies. A pending operation alone, or an unconfirmed error, does not establish withdrawal. An authorized source-state read can provide the confirmation without advancing the server operation.

Legacy numeric IDs that have lost integer precision are never used to select a server write. Local cache eviction may conservatively clear bodies in the same rounded numeric bucket while keeping source metadata; this cannot recover the exact original ID or certify physical erasure. Tracked index cleanup and untracked-copy or backup erasure remain separate statuses.

New managed API physical IDs are decimal strings. Unsafe numeric identifiers received from older endpoints cannot be edited, so the browser never rounds an ID to select a different record. Unsupported storage backends retain their existing controls and do not expose managed correction actions.

## Whole-bank deletion

When the server advertises coordinated deletion, both managed and unmanaged banks use the deletion command. Managed banks also require managed-deletion support; they never fall back to the legacy immediate-delete API. An unmanaged bank on an older backend without the coordinated capability retains legacy deletion. The dialog keeps the original operation ID while writers drain, reports active and unknown attempts, pending appends, untracked tasks and operator reconciliation requirements, and prevents accidental dismissal of the pending handle. Starting coordinated deletion opens the independent operations page with the original ID in the URL. Refreshing this page can rediscover the deletion receipt from the server even after the memory row is removed.

Receiving 202, stopping supply or reaching an index-ready state is insufficient to report deletion complete. The bank leaves the list only when the deletion operation reports `lifecycle: deleted` and `tracked_cleanup_confirmed: true`. A failed or unknown request never clears the bank or automatically resends the command. Reading status does not advance deletion; reconciliation is explicit. An in-flight attempt can still block reconciliation after its lease expires.

Confirmed deletion cancels stale bank and list reads before removing the bank's cached data and list entry, while preserving unrelated banks and the readable operation receipt. The server retains a separate authorized audit tombstone so operation status can still be read after the bank row has been deleted. Tracked cleanup does not certify erasure of backups or untraceable copies.

## Pending work and background maintenance

`/memory/:id/operations` reads the bank's authorized server inbox without requiring its configuration or capabilities. It supports pending and historical views, opaque cursor pagination and an original operation ID. The URL preserves the selected operation; a fresh page can discover pending work from the server. Deleted banks expose only their minimal deletion audit. Normal memory pages link to pending work, and confirmed closing banks clear their cached normal-supply bodies. No memory content or command payload is persisted in the URL or local storage.

The maintenance page preserves `job` and `operation` URL parameters and can reopen a recent server job. When the backend advertises persistent background execution, one explicit analysis submission queues durable work for an independently running worker. Closing or refreshing the page sends no cancellation. Read-only polling shows queued, claimed, running, completed, failed, canceled and reconciliation states; a stale heartbeat does not establish that a request has ended. Reconciliation is explicit and requires the server's permission flag. An unknown result retains its original operation, and an operator-needed state cannot be replayed from the page.

Analysis completion leaves candidates separate from active memory. Each candidate still needs review, and publication requires an explicit approved batch. Neither polling nor reopening a job approves or publishes candidates. A canceled analysis does not certify that publication stages or physical copies have been cleaned up. RAW append is available through the typed client and consumer tools; this work does not add a separate conversation-entry interface.

## Incremental source batches

When the server advertises incremental maintenance, the maintenance page links to `/memory/:id/maintenance/batches`. This requires an already managed bank and never registers sources automatically. Choose exact user, agent and session values or leave each dimension unconstrained; an empty exact value and leading/trailing spaces are preserved. Inventory covers registered, active source versions in that scope, not every physical RAW row.

Preview is an explicit read-only request. It shows effective analyzed, in-flight, blocked and eligible versions for the current coverage profile, then a bounded source plan. Whole-source mode does not read bodies or certify token fit. Optional entry IDs supply only their necessary context; they never load the whole bank. Source slots and primary limits bound the plan. Oversized whole sources can be deferred when child snapshots are created, without truncation or summaries being counted as completed analysis.

Saving a plan records metadata and stable child creation, analysis and job handles. A reserved job ID does not establish that its job exists. A separate action creates and submits at most the selected number of child jobs; reads, refresh and polling do not advance the plan. Each confirmed child links back to the existing job/candidate review page. Approval and publication remain explicit.

The selected plan ID is preserved in the URL and discoverable from the server list. Unknown creation retains its original request ID and uses an exact server lookup. An unknown submission preserves its operation ID and exact child limit in the URL; reloading only reads, and an explicit retry keeps both values. Reopening a plan from the server without those URL parameters recovers the plan and fixed child handles, not a missing parent request. A new explicit bounded submission still uses the server's stable child protocol. No command body or token is written to local storage.

Plan counts are the selection-time snapshot; progress counts children. The explicit action to read current coverage reuses the saved scope, policy, budgets and context entry IDs, with the current server model/strategy. Changed profiles can make the same version eligible again. Valid empty output may count as analyzed; failed, canceled, malformed, deferred or unconfirmed work does not. Coverage is neither factual accuracy nor approval/publication, and does not imply complete relationships across sources. Idle, blocked and terminal plans stop interval polling; active or unconfirmed work may continue read-only polling.

Cancellation stops unfinished planning and requests cancellation of created jobs. It does not certify that actual work has drained or publication-stage cleanup has completed, and does not undo already published memory. Original handles remain available for inspection.

## Long-source fragments

When the backend advertises segmentation, the source-range form offers an explicit opt-in. Whole sources remain the default, and older whole-source requests and profile identities omit segmentation settings. Fragment token and per-source part limits come from the server capability. Each fragment uses one child job; source slots still bound that primary fragment plus the necessary whole-source context from explicitly selected entries, rather than grouping several fragments into one job. Reopening a saved fragmented plan preserves its settings; a backend without the capability cannot silently reinterpret that selection as whole sources.

A segmented preview reads RAW bodies to plan and check immutable fragments, without creating analysis jobs or calling a model. Saving confirms the reviewed plan and may reread sources; a child snapshot still rechecks source versions, hashes and the full input budget. Oversized source, part-limit and context-budget exclusions appear with concrete deferral reasons. A checked preview is conditional on those frozen inputs, not a promise of execution or factual accuracy.

Each fragment has a stable fingerprint, ordinal, full source version and whole-source hash. Primary ranges are continuous, non-overlapping Unicode codepoint intervals in the original decoded source. Read ranges may include bounded adjacent context; their hashes and ranges are shown separately, and repeated context is not credited again. These positions are neither UTF-8 bytes nor JavaScript UTF-16 indexes.

The page separates frozen source selection and planned-fragment counts, live source-version coverage, and child-job progress. One analyzed fragment can leave its source partially analyzed. A whole version becomes covered only after every required fragment has valid analysis, successful execution and drained actual work. Source changes or withdrawal invalidate prior fragment coverage. Valid empty analysis can count as analyzed; deferral, malformed output, failure or cancellation does not establish full coverage.

Confirmed children link to the existing candidate review page, where fragment provenance is visible. Candidates remain hypotheses with an unverified assessment until separately reviewed; approval still does not certify factual correctness. Publication stays explicit. Fragment coverage does not imply reliable semantic merging across fragments or jobs.

## Validation tools

`node scripts/browser/verify-memory-revisions.mjs` starts an owned Vite server and real Chromium browser with controlled API responses. It checks English/light and Chinese/dark adoption, preview, pending operation, explicit reconciliation, source withdrawal and keyboard dismissal. Evidence is written under the ignored `output/playwright/memory-revisions/` directory. These fixtures do not establish real backend, provider or deployment acceptance.

`scripts/browser/verify-memory-deletion.mjs` checks the capability-driven writer notice and deletion drain, busy reconciliation and confirmed completion in English/light and Chinese/dark. Run it through the owning batch's registered validation entry point. Its helper requires the run identity and case-journal directory, reserves exact listener ports, browser profile and output before creating them, uses an owned Vite cache and checks PID/listener cleanup. It connects to an owned Chrome process in the registered process group. Labelled screenshots and results are retained under `output/playwright/managed-memory/<run-id>/`; review a contact sheet before opening individual screenshots.

For real backend acceptance, `scripts/consumers/memory-revisions.ts` exports `runMemoryRevisionConsumer`. It uses the same domain API and shared `APIClient` as the UI. Call it only with a caller-owned disposable memory containing an unmanaged derived record and its source. The consumer corrects the derived record and permanently withdraws that source; the calling fixture owns cleanup.

```sh
TSX_TSCONFIG_PATH=tsconfig.app.json node --import tsx \
  scripts/consumers/memory-revisions.ts /private/scratch-config.json
```

The private configuration supplies `baseURL` (server origin), `token`, `memoryId`, `derivedMessageId` and `sourceId` as decimal strings, `correctedContent`, `ownedScratchConfirmed: true` and an optional `resultFile`. Do not commit this file or its credentials. The consumer checks read-only preview, string IDs, revision conflict, history provenance, operation completion, withdrawal and history redaction. It does not create credentials, delete the memory bank or deploy anything. The backend may invoke the configured embedding model; use a controlled embedding fixture when real-provider calls are outside the acceptance scope.

`scripts/consumers/memory-deletion.ts` separately exports `runMemoryDeletionConsumer`. Supply `baseURL`, `token`, `memoryId`, `ownedScratchConfirmed: true` and optional `resultFile` for a disposable managed bank whose writers are already drained. It verifies the real deletion command, read-only status, explicit reconciliation, tracked cleanup confirmation and authorized operation readback after the bank row is removed. This consumer permanently deletes that scratch bank; the caller must reserve its resources before creation and independently verify cleanup. Invoke consumers through the batch's registered validation runner, without credentials on the command line.

`scripts/consumers/memory-writes.ts` exports `runMemoryWritesConsumer` with the same connection, bank, ownership and result-file configuration. Use a disposable RAW-only bank. It appends a controlled conversation, checks stable same-operation replay, rejects a different body with the same operation ID, reads the operation without advancing it and verifies decimal-string IDs. It also checks that ordinary append does not change managed mode. This consumer creates no extraction task and leaves bank cleanup to its owning fixture.

`scripts/browser/verify-memory-background.mjs` checks server inbox discovery, URL reload recovery, queued and running work, operator-needed replay prevention, candidate review, unknown publication recovery and deleted-bank audit in English/light and Chinese/dark. It uses controlled HTTP responses and an independent fixture driver for worker transitions; GET requests never advance that fixture. Run it through the registered validation entry point and review its labelled contact sheets.

`scripts/consumers/memory-background.ts` exports `runMemoryBackgroundConsumer`. The caller owns a disposable managed bank and a separately running controlled worker. ## Suggested existing targets

When advertised by the server, both the manual maintenance form and incremental batch form can suggest existing targets from one to eight explicit RAW sources and an exact user/agent scope. Empty strings are exact subjects; unrestricted scope is not converted to an empty string. Hybrid retrieval can make one embedding call, while lexical retrieval makes no model call. Recommendation, refresh and source preview do not invoke chat analysis or modify memory.

Recommendations show complete current text, revision, physical message ID, source dependencies, fingerprints and ranking reasons. Ranking scores are not factual confidence. Inventory and result budgets can omit matches, so a bounded result is not an exhaustive search. Nothing is selected by default. Check entries and apply them explicitly; only these entries and their frozen conditions become targets. Manual snapshot creation includes their required source dependencies. The batch's exact session filter still applies to that context and is never widened automatically.

Source range, subject, budget or target version changes invalidate the selection. A conflict requires fresh explicit recommendations and a new preview; the browser keeps the old snapshot rather than silently replacing its text. Known withdrawn dependencies remove recommendation bodies. Previously accepted batch target conditions can be restored from server metadata without loading a new current body, and remain attached to subsequent previews. Clear the recommendation binding explicitly to return to entry-ID input. A preview or plan creation with target conditions reads physical source/target snapshots to revalidate them; whole-source token fit still waits for child snapshot creation. It calls no chat model or child analysis. Candidate review and publication remain separate human actions.

`scripts/consumers/memory-targets.ts` exports `runMemoryTargetsConsumer`. Its caller owns a managed scratch bank, selected active registered RAW sources and a current logical target with matching exact subject scope. Supply `baseURL`, `token`, `memoryId`, decimal-string `sourceIds`, `userId`, `agentId`, `expectedTargetEntryId`, `ownedScratchConfirmed: true`, optional `query`, `excludedEntryIds` and `resultFile`. It compares hybrid and lexical read-only recommendations, verifies full current text and frozen metadata, then explicitly creates a metadata-only job and previews a batch using only the selected target. It never runs analysis, approves or publishes. Credentials stay in the caller's private configuration, and the caller reserves and cleans scratch resources. `scripts/browser/verify-memory-targets.mjs` separately checks controlled English/light and Chinese/dark desktop and narrow layouts, explicit selection, refresh without model calls and stale-target rejection; review its labelled contact sheets.

## Version-bound human verification

Where advertised by the server, a managed entry's inspector links to its verification panel and the bank's `/memory/:id/verification` queue. Human confirmation, dispute and requests for review are separate from candidate approval, memory publication and the original assessment field. A ready verification operation means its SQL record was saved; only the record's current applicability can establish that this human conclusion still matches the current binding. It is never an automatic factual guarantee.

Read a snapshot explicitly before recording an assessment. The panel shows the exact entry text, revision/hash/scope and source-version metadata. It does not automatically fetch RAW originals. Follow the explicit memory-workspace link to inspect those source IDs in the source view; if a source changed, prepare and review a new snapshot. The human supplies a method, applicable scope, notes and optional opaque evidence references. References are rendered as text and never fetched. The human-reported check time is distinct from server recording time.

Source/current-version changes invalidate old applicability. Superseded history does not occupy the latest-head review queue; revoking a current assessment can leave it needing review. Permanent withdrawal removes related human notes, evidence and applicability. Known local dependency changes fence cached and late-arriving verification reads; a failed refetch cannot establish confirmation. A bounded empty queue page does not prove that all memories were verified or that no disputes exist.

An unconfirmed command retains its original operation in the URL. Reloading performs GET reads only. An explicit retry is available only while this request's exact body is still held locally; a reload does not reconstruct that body or silently submit another operation. Normal verification routes require a live, authorized bank; they return unavailable after bank deletion. They do not replace the separate deletion audit receipt.

`scripts/consumers/memory-verification.ts` exports `runMemoryVerificationConsumer`. Supply private `baseURL`, `token`, `memoryId`, logical `entryId`, `ownedScratchConfirmed: true` and optional `resultFile`. The caller owns a live managed scratch entry and cleanup. The consumer reads snapshots/history/todos, explicitly records human confirmation and dispute, verifies same-operation replay and body conflict, reads dynamic operation applicability, revokes the latest assessment and checks the original entry/assessment remain unchanged. It never modifies memory text, calls a model or publishes candidates. `scripts/browser/verify-memory-verification.mjs` separately verifies controlled English/light and Chinese/dark desktop/narrow presentation, unknown-operation reload, version invalidation and redaction. Use the registered validation runner and review labelled contact sheets; controlled browser evidence does not establish backend or factual accuracy.

## Read-only startup context

When `startup_context.supported` is advertised, `/memory/:id/startup` offers an explicit read-time preview for exact user and agent IDs. Empty strings and surrounding spaces remain exact values; an optional exact session also constrains every necessary source. Entry IDs can be explicit, or left empty for the server's bounded inventory scan. Only currently applicable human-confirmed bindings enter this stable package. Human confirmation is a scoped judgment, not objective factual verification; the original assessment remains unchanged.

The preview includes complete entry content and complete human applicability, versioned source references, omission counts and scan/read limits. Entries and applicability are indivisible under the estimated whole-response JSON budget. An omission or bounded scan does not mean memory is false, irrelevant or forgotten. No model, memory write, promotion, analysis or publication is started. Refreshing the page does not regenerate a package. The startup response is not stored in Query/mutation data or browser persistence; local bodies disappear on changed inputs, identity, known entry/source/verification dependencies, or a confirmed closing bank. Unobserved remote changes still require a new server read.

Each included source has an explicit reader. Its requests bind the source revision, generation, full content hash and exact source scope, and fetch only a bounded Unicode codepoint span. Previous and next actions reread individual spans with live authorization; the page retains one source fragment at a time. A version mismatch or failed read clears the old preview rather than falling back to an unbound source. A visible fragment is not a claim that the entire original was reviewed. Explicit copy or JSON export produces an external snapshot that will not update when the live dependencies change; nothing is automatically injected into a conversation.

`scripts/consumers/memory-startup.ts` exports `runMemoryStartupConsumer`. Supply private `baseURL`, `token`, `memoryId`, exact `userId` and `agentId`, logical `entryId`, `ownedScratchConfirmed: true` and optional `resultFile`. The caller owns the disposable bank, lifecycle changes and cleanup. By default the consumer expects one currently human-confirmed entry and reads its bound source fragments. Optional `phaseLabel`, `entryIds` (including null for bounded inventory), exact `expectedIncluded` and `expectedOmitted: [{entryId, reason}]` let the caller independently observe pre-confirmation, dispute, stale-binding and restored phases. Explicit `expectedIncluded: []` requires empty startup text and makes no source read. Missing or budget-truncated omission details do not prove an expected reason. Optional `budgetTokens`, `maxItems` and `inventoryLimit` remain request bounds. Results return safe version/hash, omission, usage and bounded-selection observations without body text. The consumer never creates human judgments or advances the lifecycle itself. The consumer checks complete content/applicability, unchanged assessment, string version IDs, bounded Unicode continuation and repeated readback without writing or calling a model. Run through the registered validation entry point. `scripts/browser/verify-memory-startup.mjs` separately checks controlled English/light and Chinese/dark desktop/mobile rendering, explicit requests, source-change invalidation and refresh without generation; review its labelled contact sheets.
